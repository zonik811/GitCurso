Aquí es donde Git y GitHub brillan: varias personas trabajando en el mismo proyecto sin pisarse. La herramienta central es el **Pull Request**.

## El modelo de colaboración

Hay dos formas de contribuir a un repositorio:

1. **Colaborador directo**: te añaden al repo y puedes crear ramas y hacer push directamente. Común en equipos.
2. **Fork + Pull Request**: no tienes permisos de escritura, así que copias el repo a tu cuenta (fork), haces cambios y propones que los integren (PR). Común en código abierto.

## ¿Qué es un fork?

Un **fork** es una copia completa de un repositorio en **tu** cuenta de GitHub. Queda vinculado al original para que puedas proponer cambios.

```text
organizacion/proyecto   ← original (upstream)
        │  fork
        ▼
tu-usuario/proyecto     ← tu copia (origin)
```

Al clonar tu fork, conviene añadir el original como `upstream`:

```bash
git clone git@github.com:tu-usuario/proyecto.git
cd proyecto
git remote add upstream git@github.com:organizacion/proyecto.git
git remote -v
```

## ¿Qué es un Pull Request (PR)?

Un **Pull Request** es una propuesta formal de cambios: "tengo esta rama con mejoras, ¿quieres integrarla?". Permite:

- Ver el **diff** completo de los cambios.
- Comentar línea por línea (**code review**).
- Discutir, pedir ajustes y aprobar.
- Integrar (merge) cuando esté listo.

## Flujo completo de un Pull Request

### 1. Actualiza tu fork y crea una rama

```bash
git switch main
git fetch upstream
git merge upstream/main      # o: git rebase upstream/main
git push origin main         # actualiza tu fork en GitHub

git switch -c fix/typo-readme
```

### 2. Haz tus cambios

```bash
# edita archivos...
git add README.md
git commit -m "Corrige error tipográfico en la sección de instalación"
```

### 3. Sube la rama a tu fork

```bash
git push -u origin fix/typo-readme
```

### 4. Abre el Pull Request

GitHub te mostrará un botón **Compare & pull request**. Escribe:

- **Título** claro y conciso.
- **Descripción**: qué cambia, por qué, y cómo probarlo. Referencia issues: `Closes #42`.

### 5. Responde al code review

El equipo comentará. Ajusta con más commits y haz push a la misma rama: **el PR se actualiza solo**.

```bash
git add .
git commit -m "Aplica sugerencias del review"
git push
```

### 6. Se integra (merge)

Cuando lo aprueban, el mantenedor hace merge. Luego puedes limpiar:

```bash
git switch main
git branch -d fix/typo-readme
git push origin --delete fix/typo-readme
```

## Tipos de merge en GitHub

Al integrar un PR, GitHub ofrece tres opciones:

| Opción | Resultado |
| --- | --- |
| **Create a merge commit** | Historial completo con commit de merge. |
| **Squash and merge** | Combina todos los commits del PR en uno solo. Muy usado. |
| **Rebase and merge** | Reaplica los commits sin commit de merge (lineal). |

## Issues: organizar el trabajo

Los **issues** son tickets para bugs, ideas y tareas. Buenas prácticas:

- Título descriptivo y cuerpo con pasos para reproducir.
- **Labels**: `bug`, `enhancement`, `documentation`, `good first issue`.
- **Assignees**: quién lo trabaja.
- **Milestones**: agrupar issues por versión.

Cerrar un issue automáticamente al fusionar un PR:

```text
Closes #42
Fixes #42
Resolves #42
```

## Code review: dar y recibir feedback

Un buen review es específico, amable y constructivo:

- **Autor**: PRs pequeños y enfocados. Un PR de 2000 líneas nadie lo revisa bien.
- **Revisor**: comenta el *qué* y el *por qué*, sugiere, no impongas.
- Usa **suggested changes** de GitHub para proponer ediciones exactas.

<Callout type="tip">
  Empieza contribuyendo a proyectos open source con issues etiquetados `good first issue`. Es la mejor escuela y suma a tu portafolio.
</Callout>

## Proteger la rama principal

En repos de equipo, configura **branch protection** en `main`:

- Requerir PR antes de fusionar.
- Requerir al menos una aprobación.
- Requerir que pasen los checks de CI (tests).

Así nadie rompe `main` por accidente.

## Resumen del flujo colaborativo

```bash
# Preparar
git clone git@github.com:tu-usuario/proyecto.git
git remote add upstream git@github.com:organizacion/proyecto.git

# Rama de trabajo
git switch -c feature/nueva
git add . && git commit -m "Añade nueva funcionalidad"
git push -u origin feature/nueva

# Abrir PR en GitHub → review → merge → limpiar
```

## Escenario real: tu primera contribución open source

1. Encuentras un proyecto y un issue etiquetado `good first issue`.
2. Haces **fork** y clonas tu copia: `git clone git@github.com:tu-usuario/proyecto.git`.
3. Añades el original: `git remote add upstream git@github.com:organizacion/proyecto.git`.
4. Creas una rama, arreglas el issue y haces commit.
5. Subes tu rama y abres un **Pull Request** describiendo qué cambias y por qué.
6. Atiendes el review, haces push de los ajustes y, cuando lo aprueban, se fusiona.

## Errores comunes

<Callout type="warn">
  **PRs gigantes.** Un PR de 2000 líneas no se revisa bien. Divide el trabajo en PRs pequeños y enfocados.
</Callout>

<Callout type="warn">
  **Abrir el PR desde main.** Crea siempre una rama por cambio; así puedes tener varios PRs en paralelo sin mezclarlos.
</Callout>

<Callout type="danger">
  **No actualizar tu fork.** Si no sincronizas con `upstream`, tu PR partirá de una base antigua y acumulará conflictos. Haz `git fetch upstream && git merge upstream/main` antes de empezar.
</Callout>
