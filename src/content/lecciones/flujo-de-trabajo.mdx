El 90% de la confusión con Git viene de no entender **dónde viven los cambios**. Git tiene tres áreas, y tus archivos viajan entre ellas.

## Las tres áreas

```text
   Working Directory          Staging Area            Repository
   (tu carpeta)               (índice)                (.git / historial)
        │                          │                        │
        │        git add           │       git commit       │
        │  ──────────────────────► │  ────────────────────► │
        │                          │                        │
        │  ◄──────────────────────  │  ◄───────────────────  │
        │     git restore          │    git checkout        │
```

1. **Working directory** (directorio de trabajo): tu carpeta real, donde editas archivos. Aquí los cambios son "borradores" que Git observa pero aún no ha guardado.
2. **Staging area** (área de preparación o *index*): una bandeja donde colocas los cambios que quieres incluir en el próximo commit. Te permite elegir *qué* entra y *qué* no.
3. **Repository** (repositorio): el historial permanente. Cada commit es una foto guardada para siempre.

## El flujo básico

```bash
# 1. Modificas archivos en tu carpeta (working directory)
# 2. Preparas los cambios que quieres guardar
git add archivo.txt

# 3. Guardas una foto permanente en el historial
git commit -m "Añade la sección de contacto"

# 4. (Opcional) Envías al servidor remoto
git push
```

## ¿Por qué existe el staging?

Podrías preguntarte: *¿por qué no guardar todo de una vez?* El staging te da **control quirúrgico**. Imagina que tocaste tres archivos pero solo dos forman una unidad lógica coherente. Puedes commitear solo esos dos y dejar el tercero para después:

```bash
git add login.js validaciones.js
git commit -m "Corrige validación en el login"
# usuario.js queda modificado pero sin commitear, para otro commit
```

Esto produce un historial limpio y fácil de entender, algo que tus compañeros (y tu yo del futuro) agradecerán.

## Estados de un archivo

En todo momento, un archivo está en uno de estos estados:

| Estado | Significado |
| --- | --- |
| **Untracked** | Git lo ve, pero nunca lo ha rastreado. |
| **Modified** | Ya está rastreado y lo cambiaste, pero no lo preparaste. |
| **Staged** | Está preparado para el próximo commit. |
| **Committed** | Guardado en el historial. |

El comando que te dice en qué estado está todo es `git status`. Úsalo **constantemente**, es tu brújula:

```bash
git status
```

```text
On branch main

Changes to be committed:
  (use "git restore --staged <file>..." to unstage)
        modified:   index.html

Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
        modified:   estilos.css

Untracked files:
  (use "git add <file>..." to include in what will be committed)
        contacto.html
```

## El ciclo completo, visualizado

```bash
git init                 # crea el repositorio (.git)
git status               # ¿qué está pasando?
git add .                # prepara todos los cambios
git commit -m "mensaje"  # guarda la foto
git log --oneline        # revisa el historial
```

<Callout type="tip">
  Memoriza este mantra: **edito → preparo (add) → confirmo (commit)**. Repetido mil veces, es todo el día a día de Git.
</Callout>

## La carpeta `.git`

Cuando ejecutas `git init`, Git crea una carpeta oculta llamada `.git` dentro de tu proyecto. Ahí vive **todo**: el historial, las ramas, la configuración. Si borras `.git`, borras la memoria del repositorio (tus archivos quedan, pero sin historial).
