## Flujos de trabajo (workflows)

Un **workflow** es un acuerdo de equipo sobre cómo usar ramas y cómo integrar cambios.

### GitHub Flow (el más simple)

Ideal para equipos que despliegan continuamente.

```text
main  ●─────────────●──────────────●───
       \           / \            /
        ●──●──●──●    ●──●──●──●
      feature/a     feature/b
```

1. `main` siempre es desplegable.
2. Crea una rama por feature/fix.
3. Abre un Pull Request.
4. Revisa, prueba y fusiona a `main`.
5. Despliega.

**Recomendado para la mayoría de proyectos y principiantes.**

### Git Flow (más estructurado)

Para proyectos con releases versionadas. Usa varias ramas de larga vida:

| Rama | Propósito |
| --- | --- |
| `main` | Solo versiones publicadas (producción). |
| `develop` | Integración de desarrollo. |
| `feature/*` | Funcionalidades (salen de `develop`). |
| `release/*` | Preparación de una versión. |
| `hotfix/*` | Arreglos urgentes en producción. |

Potente pero pesado. Úsalo si necesitas releases planificadas.

### Trunk-Based Development

Todos commitean frecuentemente a `main` (el "tronco"), con ramas muy cortas (horas, no días) o directamente a `main` con *feature flags*.

- Máxima integración continua.
- Requiere buenos tests automatizados y CI.
- Usado por equipos de alto rendimiento.

### Comparación

| | GitHub Flow | Git Flow | Trunk-Based |
| --- | --- | --- | --- |
| Complejidad | Baja | Alta | Media |
| Ramas de larga vida | No | Sí | No |
| Releases | Continuas | Planificadas | Continuas |
| Ideal para | Web, apps | Software con versiones | Equipos maduros |

## Comandos avanzados

### `git cherry-pick` — traer un commit concreto

Aplica un commit específico de otra rama a la actual, sin fusionar todo:

```bash
git cherry-pick a1b2c3d
git cherry-pick a1b2c3d..f6e5d4c    # un rango
```

Útil para llevar un hotfix a varias ramas de release.

```bash
# Si hay conflicto
git add archivo
git cherry-pick --continue
git cherry-pick --abort
```

### `git bisect` — encontrar el commit que rompió algo

Búsqueda binaria en el historial: marca un commit bueno y uno malo, y Git te va preguntando.

```bash
git bisect start
git bisect bad                 # el actual está roto
git bisect good v1.0.0         # esta versión funcionaba

# Git hace checkout a un commit intermedio. Pruebas y respondes:
git bisect good                # o:
git bisect bad

# ... repite hasta que Git identifique el commit culpable ...
git bisect reset               # termina y vuelve a donde estabas
```

Con ~1000 commits, encuentra el culpable en unas 10 comprobaciones.

### `git blame` — quién escribió cada línea

```bash
git blame archivo.js
git blame -L 10,20 archivo.js     # solo las líneas 10-20
```

Muestra autor, fecha y hash de cada línea. Útil para entender el por qué de un código (con cuidado: no para señalar culpables).

### `git grep` — buscar en el código versionado

```bash
git grep "TODO"
git grep -n "function init"
git grep "patrón" v1.0.0          # buscar en un tag/commit
```

### `git worktree` — varios checkouts a la vez

Trabaja en dos ramas en carpetas distintas sin clonar dos veces:

```bash
git worktree add ../hotfix hotfix/urgente
git worktree list
git worktree remove ../hotfix
```

## Alias: tus propios atajos

Configura atajos para los comandos que más usas:

```bash
git config --global alias.st status
git config --global alias.co checkout
git config --global alias.br branch
git config --global alias.lg "log --oneline --graph --all --decorate"
git config --global alias.unstage "restore --staged"
git config --global alias.last "log -1 HEAD"
```

Ahora `git lg` muestra el gráfico bonito:

```bash
git lg
```

```text
* 9f8e7d6 (feature/x) Añade descuentos
* 4c3b2a1 Añade carrito
| * a1b2c3d (HEAD -> main) Corrige footer
|/
* 3e2d1c0 Commit base
```

## Limpieza y mantenimiento

```bash
git gc                        # recolecta basura y optimiza el repo
git prune                     # elimina objetos inalcanzables
git fetch --prune             # borra ramas remotas eliminadas
git remote prune origin
```

Ver el tamaño del repo:

```bash
git count-objects -vH
```

## Comandos "de rescate"

| Problema | Comando |
| --- | --- |
| "Borré un commit con reset --hard" | `git reflog` → `git reset --hard <hash>` |
| "No sé qué cambió" | `git log -p` / `git diff` |
| "El push fue rechazado" | `git pull --rebase` → `git push` |
| "Conflictos por todos lados" | `git merge --abort` y vuelve a empezar |
| "Subí un archivo por error" | `git rm --cached archivo` + `.gitignore` |
| "Necesito deshacer un commit publicado" | `git revert <hash>` |
