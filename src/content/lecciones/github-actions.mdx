Ya sabes subir código a GitHub. El siguiente salto es que GitHub trabaje **por ti**: que ejecute los tests, compile el proyecto o lo despliegue solo, cada vez que tocas el repositorio. Eso es **GitHub Actions**.

## ¿Qué es GitHub Actions?

Es el sistema de **CI/CD integrado en GitHub**. Ejecuta tareas automáticas en máquinas virtuales que GitHub te presta, llamadas **runners**, cuando ocurre algo en tu repositorio.

Antes montabas un servidor aparte (Jenkins, Travis, CircleCI). Ahora basta con un archivo de texto dentro del propio repo.

- **CI (Integración Continua)**: probar y compilar cada cambio.
- **CD (Entrega/Despliegue Continuo)**: publicar automáticamente lo que ya pasó las pruebas.
- Es **gratis** en repositorios públicos; en privados tienes una cuota de minutos al mes.

<Callout type="tip">
  Un workflow es tu red de seguridad: si un test falla, te enteras en el Pull Request, antes de fusionar. Nunca más rompes `main` sin querer.
</Callout>

## Conceptos clave

| Concepto | Qué es |
| --- | --- |
| **Workflow** | Un archivo YAML en `.github/workflows/` que define la automatización completa. |
| **Evento (`on`)** | Lo que dispara el workflow: un `push`, un `pull_request`, un horario… |
| **Job** | Un conjunto de pasos que se ejecuta en un runner. Por defecto, varios jobs corren **en paralelo**. |
| **Step** | Un paso dentro de un job: o un comando (`run`) o una acción reutilizable (`uses`). |
| **Runner** | La máquina virtual donde corre el job (`ubuntu-latest`, `windows-latest`, `macos-latest`). |
| **Action** | Una pieza de código reutilizable, publicada por GitHub o por la comunidad. |
| **Secret** | Un valor cifrado (tokens, claves de API) que nunca se escribe en el código. |

## Tu primer workflow

Todos los workflows viven en la carpeta `.github/workflows/`. Este es un `ci.yml` que compila y prueba un proyecto de Node:

```yaml
name: CI

on:
  push:
    branches: [main]
  pull_request:

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
      - run: npm ci
      - run: npm run build
      - run: npm test
```

Leyéndolo de arriba abajo:

- **`name`**: el nombre que verás en la pestaña *Actions*.
- **`on`**: cuándo se dispara. Aquí, en cada `push` a `main` y en cada Pull Request.
- **`jobs`**: la lista de trabajos. Tenemos uno, `build`.
- **`runs-on`**: el sistema operativo del runner.
- **`steps`**: la secuencia de pasos, en orden.

La diferencia entre los dos tipos de paso es la clave de todo:

<Callout type="info">
  `uses` ejecuta una **acción ya hecha** (`actions/checkout` descarga tu repo). `run` ejecuta un **comando de shell** que tú escribes (`npm test`). Si existe una acción para algo, úsala; si no, `run`.
</Callout>

## Los eventos que lo disparan

El bloque `on` es el interruptor. Estos son los más útiles:

| Evento | Se dispara cuando… |
| --- | --- |
| `push` | Subes commits. Puedes filtrar por rama con `branches: [main]`. |
| `pull_request` | Alguien abre o actualiza un Pull Request. |
| `schedule` | Según un horario en formato cron. |
| `workflow_dispatch` | Le das al botón **Run workflow** a mano. |
| `release` | Publicas una versión. |

```yaml
on:
  schedule:
    - cron: '0 3 * * 1'   # cada lunes a las 3:00
  workflow_dispatch:       # botón manual en la interfaz
```

<Callout type="tip">
  `workflow_dispatch` es oro para depurar: te deja lanzar el workflow cuando quieras, sin esperar a hacer un push.
</Callout>

## Secretos y variables

Nunca pongas una clave en el YAML: cualquiera que vea el repo la vería. Guárdala en **Settings → Secrets and variables → Actions** y úsala así:

```yaml
- run: npm run deploy
  env:
    API_KEY: ${{ secrets.API_KEY }}
```

Los secretos se muestran como `***` en los logs.

<Callout type="warn">
  Un secret no es magia: si tu script lo imprime o lo pasa a un servicio externo, se filtra. Úsalo solo en variables de entorno y evita hacer `echo`.
</Callout>

## Matrices y caché

Para probar varias versiones de un lenguaje, usa una **matriz** y GitHub crea un job por combinación:

```yaml
strategy:
  matrix:
    node: [18, 20, 22]
```

Y para no descargar dependencias en cada ejecución, activa la **caché**:

```yaml
- uses: actions/setup-node@v4
  with:
    node-version: 20
    cache: npm
```
