Las ramas son la función estrella de Git. Permiten que varias líneas de trabajo convivan sin interferirse: una para `main`, otra para tu nueva funcionalidad, otra para un experimento. En esta lección verás, con animaciones, cómo nacen, cómo se mueven y cómo se vuelven a unir.

## ¿Qué es una rama?

Una rama es simplemente un **puntero móvil a un commit**. No es una copia de los archivos: es una etiqueta que apunta a un punto del historial. Por eso crear una rama en Git es instantáneo y no ocupa espacio, aunque el proyecto pese gigabytes.

Cuando haces commits en una rama, su etiqueta avanza sola al commit más reciente. Mira cómo ocurre de verdad:

## ¿Y qué es HEAD?

`HEAD` es un puntero especial que indica **dónde estás**. Normalmente apunta a la rama en la que estás trabajando (no directamente al commit), y a través de ella al último commit.

- Si `HEAD` apunta a `main`, tus commits avanzan `main`.
- Si `HEAD` apunta a `feature`, tus commits avanzan `feature`.
- Cuando cambias de rama con `git switch`, `HEAD` se mueve y **tu working directory se actualiza** al contenido de esa rama.

En la animación anterior, la etiqueta con el borde de color y el distintivo `HEAD` marca siempre dónde estás. Verás que al hacer `git switch main` el contenido cambia: `feature.txt` desaparece de tu carpeta porque ese archivo pertenece a la otra rama.

## Comandos de ramas

### Ver ramas

```bash
git branch              # ramas locales (* marca la actual)
git branch -a           # incluye ramas remotas
git branch -v           # con el último commit de cada una
```

```text
* main
  feature-login
  experimento
```

### Crear una rama

```bash
git branch feature-login              # crea, pero no te mueve
git switch -c feature-login           # crea Y te mueve (recomendado)
git checkout -b feature-login         # forma clásica equivalente
```

### Cambiar de rama

```bash
git switch main            # forma moderna (Git 2.23+)
git checkout main          # forma clásica
```

`checkout` hace muchas cosas (cambiar rama, restaurar archivos, ir a un commit), así que Git introdujo `switch` (para ramas) y `restore` (para archivos) para mayor claridad. Usa los nuevos.

### Renombrar y borrar

```bash
git branch -m nuevo-nombre          # renombrar la rama actual
git branch -m viejo nuevo           # renombrar otra
git branch -d feature-login         # borrar (solo si está fusionada)
git branch -D feature-login         # borrar a la fuerza
```

## ¿Qué es fusionar (merge)?

Fusionar significa **traer los commits de otra rama a la tuya**. Siempre te colocas en la rama que **recibe** y fusionas la otra:

```bash
git switch main           # te pones en la rama destino
git merge feature         # traes feature hacia main
```

Git elige entre dos formas según el historial:

### Fast-forward (avance rápido)

Si `main` **no ha cambiado** desde que creaste `feature`, no hay nada que combinar: Git solo mueve la etiqueta `main` hasta el último commit de `feature`. No se crea ningún commit nuevo.

### Fusión con commit de merge (three-way)

Si **ambas ramas avanzaron**, Git no puede limitarse a mover el puntero: crea un **commit de merge** que tiene dos padres (el último de cada rama). Es el rombo que viste en la primera animación.

<Callout type="info">
  Si las dos ramas han tocado **la misma línea** del mismo archivo, Git no puede decidir y aparece un **conflicto**. No es un error: es Git pidiéndote que elijas. Lo resolvemos en detalle en la lección de **Fusiones**.
</Callout>

## ¿Qué es `git pull`?

`git pull` sirve para **traer los commits del repositorio remoto** (por ejemplo, los que subió un compañero) a tu rama local. Por dentro hace dos cosas:

1. **`git fetch`**: descarga las novedades del remoto sin tocar tu trabajo.
2. **`git merge`**: las integra en tu rama actual.

Es decir, `git pull` = `fetch` + `merge`. Por eso, **antes de empezar una rama**, conviene actualizar `main`:

```bash
git switch main
git pull                  # trae lo último del equipo
git switch -c feature-carrito
```

Así tu rama parte de la base más reciente y evitas conflictos innecesarios. Lo veremos a fondo en la lección de **Repositorios remotos**.

## Practica las ramas

Esta terminal **sí entiende de ramas**. Crea un commit base y luego juega con `git branch`, `git switch` y `git branch -d`. Mira el panel **Ramas**: el punto ● marca dónde estás (HEAD).

<Callout type="info">
  Prueba: `git init` → `git add .` → `git commit -m "Base"` → `git branch feature` → `git switch feature` → `echo "nuevo" > feature.txt` → `git add .` → `git commit -m "Trabajo en feature"` → `git switch main`. Observa que `feature.txt` **no** está en main: cada rama tiene su propia línea de trabajo. Termina con `git merge feature`.
</Callout>

## Cambiar de rama con cambios sin guardar

Si intentas cambiar de rama con cambios sin commitear, Git te lo impedirá si hay conflicto. Opciones:

```bash
git stash                  # guarda temporalmente tus cambios
git switch otra-rama
git stash pop              # los recupera aquí
```

O commitea primero (aunque sea un WIP), o usa `git switch -m` para intentar llevar los cambios. El `stash` lo veremos en detalle más adelante.

## Ramas como espacio de experimentación

Una de las grandes ventajas: puedes probar algo arriesgado sin tocar `main`. Si funciona, fusionas; si no, borras la rama y **no queda rastro**.

```bash
git switch -c experimento-loco
# ... haces destrozos ...
git switch main
git branch -D experimento-loco      # adiós, sin consecuencias
```

## Escenario real: una funcionalidad sin romper main

Trabajas en una tienda online y te piden añadir un cupón de descuento. En lugar de tocar `main` directamente:

```bash
git switch main
git pull
git switch -c feature/cupon-descuento
# ... programas el cupón, commiteas ...
git push -u origin feature/cupon-descuento
# abres un Pull Request
```

Si algo sale mal, `main` sigue intacto. Cuando el PR se aprueba y se fusiona, borras la rama.

## Errores comunes

<Callout type="warn">
  **Cambiar de rama con cambios sin guardar.** Git te bloqueará si hay conflicto. Guarda con `git stash` (o commitea) antes de cambiar.
</Callout>

<Callout type="warn">
  **Trabajar siempre en main.** Crea una rama por tarea; así `main` queda siempre desplegable y no arriesgas el trabajo del equipo.
</Callout>

<Callout type="danger">
  **Borrar una rama sin fusionar.** `git branch -d` avisa, pero `-D` la borra a la fuerza y puedes perder commits. Comprueba antes con `git log` o `git branch --merged`.
</Callout>
